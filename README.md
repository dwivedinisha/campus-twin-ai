# CampusTwin AI

**Agentic AI-Driven Digital Twin for Autonomous Smart Campus Resource Optimization**

A simulation-first digital twin platform for a virtual smart campus, covering real-time monitoring, ML-based prediction, anomaly detection, and what-if resource optimization — built entirely on synthetic (but statistically calibrated) telemetry, with an architecture designed to accept real IoT sensor data later without redesign.

---

## What This Is

CampusTwin AI models a virtual campus of 3 buildings and 30 rooms, generating realistic occupancy, temperature, humidity, and energy telemetry through a custom simulation engine — not random noise, but behavior grounded in real campus patterns (class schedules, day/night cycles, seasonal drift) and calibrated against a real public building-energy dataset.

On top of that data, the system runs machine learning models to predict occupancy and energy consumption, detect anomalies (like AC failures), and simulate hypothetical scenarios ("what happens if we turn off the AC in this room?") — all surfaced through a live API and a React dashboard.

> **All data in this system is clearly synthetic (`data_source: SIMULATION`)**. No real campus hardware or student data is used. See [Data Source Transparency](#data-source-transparency).

## Data Source Transparency

Every row of telemetry in this system carries a `data_source` field:

- `SIMULATION` — historical data generated by the offline simulator
- `SIMULATION_LIVE` — data generated by the live Digital Twin engine

Real IoT data, when eventually integrated, will be tagged `LIVE_IOT`. The system is designed to never blend or mislabel synthetic and real data.

A real public dataset (Kaggle: *Energy Consumption, Temperature, Occupancy*) was used **only to calibrate simulator parameters** (e.g., the relative strength of temperature vs. occupancy as energy drivers) — it was never loaded into the system's own dataset. See `simulator/calibration/`.

## Setup (Windows)

### Prerequisites
- Python 3.11+
- PostgreSQL 16+
- Node.js LTS
- Git

### 1. Clone and set up Python environment
```powershell
git clone https://github.com/YOUR_USERNAME/campus-twin-ai.git
cd campus-twin-ai
python -m venv venv
venv\Scripts\activate
pip install -r requirements.txt
```

### 2. Configure environment variables
```powershell
copy .env.example .env
```
Edit `.env` and set your PostgreSQL password.

### 3. Create the database
```powershell
psql -U postgres
```
```sql
CREATE DATABASE campustwin;
\q
```

### 4. Generate simulation data
```powershell
python simulator\run_simulator.py
```

### 5. Load schema and data
```powershell
cd db
python create_schema.py
python load_data.py
cd ..
```

### 6. Train ML models
```powershell
python ml\training\train_occupancy_model.py
python ml\training\train_energy_model.py
python ml\training\train_anomaly_model.py
```

### 7. Run the backend
```powershell
cd backend
uvicorn main:app --reload
```
API docs available at `http://127.0.0.1:8000/docs`

### 8. Run the frontend
```powershell
cd frontend
npm install
npm run dev
```
Dashboard available at `http://localhost:5173`

## Simulator Realism Details

The campus simulator is not a random-number generator. It models:

- **Time-of-day occupancy curves** — separate weekday/weekend profiles reflecting real class schedules (near-zero at night, sharp peaks during class hours, lunch dip)
- **Seasonal temperature drift** — a slow cosine wave layered under the daily temperature cycle, spanning a configurable period
- **Non-linear AC response** — energy draw from cooling rises faster than linearly as outdoor temperature climbs further above the comfort threshold
- **Autocorrelated ("sticky") noise** — sensor fluctuations persist across consecutive readings (AR(1) process) rather than resetting independently each interval, matching how real sensors behave
- **Injected, labeled anomalies** — AC failures and unexpected-occupancy events occur at a calibrated rate and persist for a realistic duration, with ground-truth labels retained for anomaly-detection evaluation

Parameters (`ac_power_kw`, `temp_sensitivity`, `base_load_kw`, etc.) were calibrated by analyzing a real public building-energy dataset (Kaggle) for the *relative* importance of temperature vs. occupancy as power drivers — see `simulator/calibration/analyze_real_data.py`.

## Design Principles

- **Simulation-first, hardware-never-required.** No real IoT hardware is assumed or needed to run this system end to end.
- **Data source transparency.** Every reading is labeled with where it came from; synthetic data is never presented as real.
- **Frontend never touches the database.** All access goes through the FastAPI backend, keeping the architecture swap-ready for real sensors later.
- **Modular monolith, not microservices.** Kept intentionally simple — no Kubernetes, no distributed system complexity — appropriate for the current project scale.
- **Human-in-the-loop for consequential actions.** No AI-to-actuator path is fully automatic; approval steps are mandatory for anything that changes simulated (and eventually real) campus state.
